# Audit of the inkpdf service through its MCP interface

- **Date**: 2026-10-12.
- **Service**: inkpdf 0.1.0, branch `004-mcp-server`, started with Docker Compose at `http://localhost:3000/mcp`. MCP protocol 2025-06-18.
- **Templates**: `sample` 1.0.0, `packages-demo` 1.0.0 and `progress-invoice` 1.0.0, i.e. every template returned by `list_templates`.
- **Method**: black box, only through the MCP tools `list_templates`, `get_template` and `render_template`, plus a few raw JSON-RPC calls. No code was changed. All data is fictitious.
- **Out of scope**: Factur-X and e-invoicing.
- **No fixes**: this report lists defects only; it does not propose code changes.

## Volume and method

- **Cases run**: 472 in total.
  - `sample` and `packages-demo`: 174 cases, 101 of them producing a PDF.
  - `progress-invoice`, validation: 207 cases, plus 11 raw JSON-RPC calls.
  - `progress-invoice`, rendering and amounts: 80 cases, 71 of them producing a PDF.
- **PDFs**: 172 PDFs from nominal and edge cases (101 for sample and packages-demo, 71 for progress-invoice). All pass `qpdf --check`. Inputs that validation should have refused also produced PDFs; for those, only the extracted text was checked.
- **Amount checks**:
  - **progress-invoice**: the printed amounts were recomputed in Python with `Decimal`: **6,116 amounts in 71 PDFs, no amount off by a cent**. The only gaps are in what is displayed (defect 12) and in the amount in words (defects 10 and 43).
  - **packages-demo**: only the formatting of the input amount was checked, with 25 cases.
  - **sample**: it computes nothing.
- **Visual checks**:
  - `sample` and `packages-demo`: every page was looked at, one by one or on a contact sheet.
  - `progress-invoice`: every page went through automatic checks (overlapping text, margins, footer, page numbering, font of each character). A subset of pages was also looked at.
- **Evidence**: each case had its argument file, the MCP response and, when relevant, the PDF, the extracted text and PNG renderings. They were kept outside the repository, in three folders: `A/` (sample and packages-demo), `B/` (progress-invoice validation) and `C/` (progress-invoice rendering). They are not committed; the file names are kept below for traceability. The original IDs (A-xx, B-xx, C-xx) are given in parentheses.
- **Not checked**: decoding the QR code of `packages-demo`, since no decoder was installed. The SEPA QR code of `progress-invoice` was decoded and checked.

**Status**
- **OBSERVED**: an output file shows the defect.
- **ASSUMED**: the defect rests on an external rule (law, trade practice, standard) or on a consequence that could not be checked.

## Summary

| Severity | Count |
|---|---|
| Blocking | 2 |
| Major | 20 |
| Minor | 42 |
| **Total** | **64** |

The three parts of the audit found 88 defects, some of them twice; merged, 64 remain.

**Main points**
1. **The SEPA QR code, on by default, prevents rendering invoices that are valid against the schema.** A reference longer than 35 characters, or an accented 69-character company name, is enough. The assistant gets "Tell the operator" and cannot recover on its own.
2. **Some wrong data ends in a compilation error instead of a validation refusal.** This covers impossible dates, invalid IBANs and BICs, and references too long for a QR code. The message points to an internal file, not to the faulty field, and says "Tell the operator".
3. **Absurd documents are accepted without any signal**: negative amount due, 50 % retention, empty required fields. Nothing shows it in the `render_template` answer either, which only gives the file name and size.
4. **The amounts are right, but some wording misleads**: the amount in words is called "TTC" although it is the amount due, the law quoted is wrong, and the printed quantity × unit price does not give the printed amount.
5. **The layout breaks in common cases**: the New Computer Modern font, large amounts, long words without spaces.

## MCP usability

- **Are the descriptions enough to fill the data without guessing?**
  - The three tools are well described, and the server instructions give a clear path: list the templates, read the schema, ask for the missing fields, then render.
  - The template schemas are what leaves room for guessing (defect 07). `sample` has no description at all. `progress-invoice` lacks units, whether amounts are before or after tax, the meaning of amendments and the QR limits.
- **Can an agent fix its input at the first try from the error messages?**
  - **Yes, for everything the schema describes.** The JSON path is exact, the received value is quoted, every violation is listed at once (up to 22 in one case), and a closing hint says what to do.
  - **No, for what the schema does not describe**: impossible dates, IBAN, BIC, lengths imposed by the QR code. Rendering then fails with "Tell the operator" and an internal file path (defects 01 to 05). An agent concludes that the service is broken instead of asking the user for the field again.
- **Does the `render_template` answer allow checking the result without opening the PDF?** No: it only gives the file name and size (defect 06).

## What works well

- **progress-invoice amounts**: 6,116 amounts recomputed with not a single cent of difference, including above 13 million €, with four VAT rates and under reverse charge. The amount in the decoded SEPA QR code always equals the amount due.
- **Schema validation**:
  - `progress-invoice` is closed everywhere: an unknown property is refused at every level.
  - The amount pattern is strict: comma, space, "+", ".5" and 5 decimals are refused.
  - Types, bounds and enums are checked, with precise messages.
  - No input invalid against the schema caused a compilation error in `sample` or `packages-demo`.
- **PDFs**:
  - The 172 checked PDFs pass `qpdf --check`.
  - Output is deterministic: two renderings of the same data are byte-identical.
  - Fonts are embedded.
  - PDFs are tagged, with language `fr-FR`.
  - Metadata is written correctly.
- **Pagination**:
  - "page x / n" is right on every page of progress-invoice.
  - The table header is repeated at the top of each page.
  - The footer is never overlapped.
  - `sample` handles 3000 rows (74 pages) in 5 seconds.
- **Amount typography in progress-invoice**: thin non-breaking thousands separator, non-breaking space before "€" and "%", a real minus sign, decimal comma. The amount in words is right in the vast majority of cases ("soixante et onze", "quatre-vingts", "deux cents").
- **Security**:
  - Typst markup slipped into the data (`#pagebreak()`, `*bold*`) is printed as is, never run.
  - `filename` is sanitised: `../x` becomes `x.pdf`.
  - Size limits are enforced.
- **Layout options**: every enum value and every boolean produces a PDF with the expected effect, except for defects 16, 46 and 48.
