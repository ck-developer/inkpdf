# Architecture

inkpdf is a single Rust binary: an [axum](https://docs.rs/axum) HTTP server with the Typst
compiler embedded as a library. It starts no subprocess and no browser.

## Repository layout

The repository is a Cargo workspace:

| Path | Content |
|------|---------|
| `crates/inkpdf/` | The service: library (`src/lib.rs`), binary (`src/main.rs`), `build.rs`, tests and benchmarks. |
| `xtask/` | Maintainer commands, run with `cargo xtask …` (docs generation, bundled packages). Not part of the image. |
| `packages/` | Bundled Typst packages: `lock.toml` and the official archives in `vendor/`. |
| `openapi/openapi.json` | Locked OpenAPI document of the generic routes, checked by a contract test. |
| `examples/` | Example templates, request bodies and a Bruno collection. |
| `docs/` | This mdBook site. |
| `specs/` | Feature specifications, plans and contracts. |

## Modules

The `inkpdf` crate (`crates/inkpdf/src/`) is split into:

| Module | Role |
|--------|------|
| `main.rs` | Entry point. `inkpdf [serve]` reads the configuration, runs the initial scan, starts the watcher and the server, and handles graceful shutdown. `inkpdf healthcheck` queries `/health` for the Docker `HEALTHCHECK`. |
| `lib.rs` | `AppState`, shared by the handlers: configuration, registry, render slots (a semaphore) and the live OpenAPI cache. |
| `config.rs` | The `INKPDF_*` variables (see [Configuration](../reference/configuration.md)). |
| `error.rs` | `ApiError` and its RFC 9457 `problem+json` rendering, with the error codes. |
| `api/` | HTTP routes and the OpenAPI document. |
| `registry/` | Discovery, loading and hot reload of the templates. |
| `template/` | The template model: id, `template.json` manifest, `schema.json`, package imports. |
| `render/` | The rendering pipeline: sandboxed `World`, fonts, JSON to Typst values, PDF metadata. |
| `packages/` | The bundled Typst packages, generated by `build.rs`. |

### `api/`

- `templates.rs`, `render.rs`, `packages.rs`, `health.rs`: the handlers, each annotated with
  `utoipa` so that the OpenAPI document is generated from the code.
- `mod.rs` builds the router, the body size limit and the static OpenAPI document (the generic
  routes). That document is locked in `openapi/openapi.json` by the `contract_openapi` test.
- `live.rs` serves `GET /openapi.json`: the static document extended, at request time, with one
  typed render operation per valid template, whose request body is the template's own schema.
  The result is cached and rebuilt only when the registry snapshot changes.
- `docs.rs` serves `GET /docs`: a static page that loads the Scalar API reference (pinned
  version) in the browser and points it at `/openapi.json`.

### `registry/`

- `mod.rs`: the `Registry`, a map from template id to `TemplateEntry` behind an `ArcSwap`.
  Readers get a consistent snapshot; every update builds a new map and publishes it at once.
- `fingerprint.rs`: walks a template folder without reading contents and hashes each file's
  relative path, size and modification time. Hidden files are skipped; symbolic links are
  followed only if their target stays inside the folder. The walk also gives the total size,
  checked against `INKPDF_MAX_TEMPLATE_BYTES` before anything is read.
- `loader.rs`: the only place where template files are read. It loads the folder into an
  in-memory snapshot, parses the manifest and the schema, loads the template fonts, and
  rewrites package imports to their installed version. A template that fails any check becomes
  an *invalid* entry with a reason; it never stops the service.
- `watcher.rs`: hot reload. File system events (`notify`, debounced over 500 ms), plus a
  periodic rescan every `INKPDF_RESCAN_INTERVAL_SECS`, trigger a refresh. A template is reloaded
  only when its fingerprint has changed **and** stays the same at a confirming observation
  one second later, so a half-copied folder is never loaded; meanwhile, the previous version is
  still served.

### `render/`

- `world.rs`: `SandboxWorld`, the Typst `World` implementation. It serves only the template's
  in-memory snapshot and the bundled packages (each package sees only its own files), plus
  fonts. It exposes `data` and `layout` as `sys.inputs`. It reads no disk, network or
  environment variable. It checks a cancellation flag on every file and font access.
- `fonts.rs`: the fonts embedded in the binary plus the template's `fonts/` folder; system
  fonts are never loaded.
- `value.rs`: conversion of JSON values into Typst values.
- `metadata.rs`: the optional `metadata` section of the body, validated against a fixed schema
  and applied to the compiled document (never injected as Typst code).
- `mod.rs`: the pipeline, described below.

### `packages/` and `build.rs`

`build.rs` reads `packages/lock.toml`, verifies the SHA-256 digest of each archive in
`packages/vendor/`, extracts it, checks its manifest and generates a static table whose files
are included with `include_bytes!`. Any inconsistency fails the build, naming the package.
`packages/mod.rs` exposes that table: `selected` packages are offered to templates (one version
per name); `dependency` packages only serve imports between packages.

## Request flow

`POST /templates/{templateId}/render`:

1. The template id is validated (`^[a-z0-9][a-z0-9_-]{0,63}$`) and looked up in the registry
   snapshot (`404`). The query (`download`, `filename`) is parsed (`400`).
2. The content type must be JSON (`415`); the body is limited by `INKPDF_MAX_BODY_BYTES`
   (`413`) and must be a JSON object (`400`).
3. An invalid template answers `409`.
4. `metadata` is validated against the service's schema; `data` and `layout` against the
   template's schema, after `layout` defaults are applied. All violations are returned
   together (`422`). Nothing is compiled before this point.
5. `render::render` waits for a render slot, at most `INKPDF_QUEUE_TIMEOUT_SECS` (`503`).
6. The compilation runs on a blocking thread: a `SandboxWorld` is built, Typst compiles the
   document, the metadata is applied and `typst-pdf` exports it. The PDF identifier is derived
   from the template id and fingerprint, and no timestamp is written, so the same template and
   body give the same bytes.
7. If the compilation does not finish within `INKPDF_RENDER_TIMEOUT_SECS`, the caller gets
   `504` and the cancellation flag is set; the world then fails every file and font access.
8. The slot is held by a `RenderGuard` that lives on the compilation thread: it is released
   only when the compilation really ends, even after a timeout or a panic, and logs
   `render.overrun` if it ended after its deadline.
9. The PDF is returned with a `Content-Disposition` header built from the cleaned filename.

One `render` log event records the template id, the duration and the outcome; the body is never
logged.

## Startup

`main.rs` reads the configuration (exit code `2` on a malformed value), initialises logging,
scans the whole volume, marks the registry ready, starts the watcher, then binds the listener.
`SIGTERM` or `Ctrl-C` triggers a graceful shutdown.

## Design principles

The project constitution (`.specify/memory/constitution.md`) sets the rules every change must
respect, among them:

- PDFs are generated only by the embedded Typst engine; no subprocess, no browser.
- A template is a self-contained folder; it never needs the network or files outside itself.
- Callers send only JSON, validated against the template's schema before any compilation, and
  injected as data.
- The engine runs sandboxed, and every render is bounded in size and time.
- Templates are hot-loaded; the binary and image are fixed.
- The API is a self-describing REST API (OpenAPI).
- Simplicity first: no authentication, no users, no document-specific logic.
